Project briefing

A concise walkthrough of the problem, the design choices, and what this demonstration does and does not establish.

Why this problem matters

Detection systems can identify suspicious traffic but leave response to a separate operator or tool. In a switched network, a slow response gives an attacker time to move between services, while manual per-switch changes are inconsistent and hard to audit.

This project demonstrates a local pipeline from packet inspection to a correlated incident and a time-bounded network policy, with analyst review and protected infrastructure addresses.

What is distinctive here

  • Suricata signatures feed an incident engine rather than triggering isolated responses.
  • Alerts are grouped by source, enriched with STRIDE and MITRE ATT&CK references, and given a readable response rationale.
  • OS-Ken applies OpenFlow rules across connected switches; the dashboard exposes topology, flows, evidence, and analyst decisions.
  • A protected-IP allowlist and expiring rules reduce the risk of blocking essential infrastructure indefinitely.

The contribution is the explainable integration and demonstration workflow; this is a prototype, not a claim of novel detection algorithms or production-grade efficacy.

How to read this demo

The offline mode replays a small, labelled set of EVE-style records. Its topology and flows are simulated from those records. Proposed responses are explicitly marked simulated; they do not block packets.

The live lab connects Mininet, Suricata, OS-Ken, and the orchestrator. Controller submission is not proof of packet loss: verify the switch flow table and traffic behavior in the isolated lab.

Why these scenarios and controls

The project includes lab-oriented port-scan, SYN/UDP/ICMP flood, SSH/HTTP credential, SQL-injection, and ARP-spoofing modules. The replay intentionally models only a safe set of alert records; it does not run those scripts or generate attack traffic. The selected records span reconnaissance, availability, authentication, application-layer, IoT, and name-resolution cases so reviewers can trace how different evidence is handled.

Controls are chosen by evidence strength and network scope: signatures identify known patterns; correlation groups related records by source; protected addresses prevent self-inflicted outages; lower-confidence or medium-severity activity is monitored or rate-limited; stronger evidence can trigger a bounded source block; and analyst actions can resolve or suppress false positives. The rate limiter uses switch meters, while blocks use expiring IPv4 source rules.

Practical boundary: network containment can reduce lateral reach, but it does not fix vulnerable applications, replace MFA or account lockout, or establish that a rule is accurate. Validate each policy in the isolated live lab before relying on it.

Evaluation plan: demonstrate each scenario in the isolated lab, inspect the matching EVE record and incident rationale, verify the submitted flow on every switch, then compare before/after connectivity. Report precision, recall, false positives, and mitigation time only after testing against labelled traffic; the demo does not claim those measured results.
